# AI 协作治理

本文档定义需要由团队成员、评审者和模块 owner 执行的治理制度。它不是 Agent 的自动执行清单。

## 1. 三重审查

AI 参与生成或修改的代码在合入前应同时满足：

1. **能运行**：有与风险匹配的测试、构建或行为验证证据；
2. **能解释**：至少一名评审者能说明代码为何存在、为何采用当前方案以及主要边界；
3. **能维护**：明确后续负责该模块的人，出现问题时有人能够接手。

任一条件不满足时，不应仅因为代码表面可用就合入。

## 2. Intent Review

评审 AI 产出时，重点确认：

- 变更解决的真实问题与验收标准；
- 采用当前方案而放弃其他方案的原因；
- 关键假设、失败模式和回退方式；
- 与团队环境相关的参数和协议，例如 API 版本、错误码、连接池、超时、重试和限流策略。

不要求逐行复述代码。评审者应能解释关键控制流、边界和决策；无法解释的部分视为意图债，应在合入前补足理解或记录。

## 3. Ownership

- 每个重要模块至少有一名明确 owner，能够说明模块职责、主要依赖和关键设计决策。
- 无人能够解释的模块标记为认知债热点，优先安排阅读、测试补强或重构。
- AI 可以辅助整理调用关系和决策记录，但不能替代人的最终 Ownership。

## 4. 理解预算

- 团队可根据 AI 代码占比和变更风险，为每个迭代预留约 20%–30% 的容量，用于阅读、审查、测试补强和必要重构。
- 百分比是治理建议，不是所有项目的固定指标；应通过返工率、缺陷率和评审质量调整。
- 当团队已无法解释或安全维护新增代码时，应暂停继续扩大 AI 代码规模，先偿还认知债。

## 5. 决策归属

- AI 可以提出候选方案、证据、成本和风险。
- 公共 API、数据兼容性、安全边界、生产依赖和核心架构等高影响决策由人拍板。
- 关键决策应记录在 ADR、任务报告、issue 或 PR 中，选择一种团队实际维护的载体即可，避免重复记录。

## 6. 债务对应关系

| 债务类型 | 治理机制                                |
| -------- | --------------------------------------- |
| 认知债   | 能解释审查、模块 Ownership、理解预算    |
| 意图债   | Intent Review、关键决策记录、意图型注释 |
| 决策债   | 高影响决策由人确认，AI 提供候选与证据   |
| 技术债   | 最小实现、验证门槛、定期测试补强与重构  |
