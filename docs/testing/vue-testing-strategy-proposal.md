# Vue 测试体系替代方案

状态：待实施的设计方案，2026-09-13。本文不改变当前验收契约、覆盖账本或历史证据；实施时按通过验证的切片逐步切换入口。

## 建议与依据

目标栈为 **Vitest + Vue Test Utils + jsdom / Node，Storybook Vue 3 + Vite，Playwright Test**。对齐 Semi 的测试分层和公开行为，用 Vue 原生工具替换 React 的 Jest/Enzyme 用法；减少重复状态验证与自建验收调度，不重写整套组件、文档站和构建链。

Vue 官方推荐 Vitest 和 Vue Test Utils；Element Plus、Naive UI 当前官方仓库也采用这一组合，并将 SSR、文档类型或产物检查另设入口。这是生态成熟度依据，不代表它们的行为可以替代 Semi 基线，也不代表 Vitest 在本仓库一定更快。[Vue 测试指南](https://vuejs.org/guide/scaling-up/testing.html)、[Element Plus 配置](https://github.com/element-plus/element-plus/blob/dev/vitest.config.mts)、[Naive UI 配置](https://github.com/tusen-ai/naive-ui/blob/main/vite.config.mts)。

本仓库已有 Vue Test Utils；需要替换的是 Rstest runner/API 和相应配置。历史同环境单次记录为 Vitest 51.67 秒、Rstest 35.1 秒，且 Rstest 有 Vue 覆盖率补丁。因此采用 Vitest 的理由是生态集成、配置和维护成本，不能宣称 runner 替换会提速。[迁移记录](../../ai-work/20260910-103000-rstack-migration.md#第四阶段单测迁移到-rstest)。

Storybook 提供正式的 Vue 3 + Vite 集成。它在本方案中负责场景组织和调试，浏览器断言统一由现有 Playwright Test 承担；暂不同时加入 Storybook test-runner、Cypress 或 addon-vitest。后者官方支持 Vue/Vite，但现在接入会增加另一套浏览器执行入口，收益尚未验证。[Vue 集成](https://storybook.js.org/docs/get-started/frameworks/vue3-vite)、[Vitest addon](https://storybook.js.org/docs/writing-tests/integrations/vitest-addon)。

版本在实施时核对 Vue、Node、Vite、插件的 peer 范围并锁定稳定补丁版；不直接照搬生态仓库版本，不依赖预览版功能。现有 Playwright 常规页面测试足够承载方案，不需要引入新的组件挂载运行时。

## 每一层只承担明确的责任

| 层次                | 推荐工具与载体                                          | 核心职责                                                             | 与固定 Semi 的关系                                       |
| ------------------- | ------------------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------- |
| 源码与类型          | TypeScript、vue-tsc、现有 ESLint                        | 公开 props/emits/slots 类型、exports、源码质量                       | 将 React 专属 API 映射为 Vue 契约                        |
| 单测与 DOM 组件测试 | Vitest + Vue Test Utils；默认 jsdom，SSR 使用 Node      | props、emits、slots、v-model、受控更新、事件顺序、异步完成和卸载清理 | 迁移上游行为用例的输入与预期，不照抄 Enzyme 调用         |
| 组件浏览器对照      | Storybook Vue 场景 + Playwright；React 保留固定参考应用 | 真实焦点、Portal、几何、主题、RTL、拖拽、滚动、动效、关键像素        | 同环境运行真实 React/Vue，用相同输入和可观察结果核对     |
| 文档集成            | 现有 Nuxt 文档站 + Playwright                           | 每个双语示例的加载和主要演示操作；源码展示、链接、编辑器及多文件依赖 | 文档内容与固定双语片段对应；有独特集成风险的示例保留专项 |
| 发布消费            | 现有 SSR、主题、tarball、隔离安装脚本                   | 无 DOM 导入、实际 exports/CSS、Vue/Nuxt 消费、发布包完整性           | 验证 Vue 包交付契约，不用源码单测代替                    |

普通逻辑在单测层系统覆盖；真实浏览器独有风险必须在浏览器验证。一个交互链有明确的主要测试位置，只有不同入口确实带来独立故障面时才重复深测。jsdom 的通过不能证明布局正确，文档页面能加载也不能证明示例交互正确。

## 如何替换当前体系

| 当前部分                                                 | 目标处理                                                                                                  |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Rstest 单测与覆盖率配置                                  | 分组迁移到 Vitest；保留现有测试、发现范围、环境与有效断言，验证后再移除 Rstest 及仅其使用的补丁           |
| 自建 Vue 对照工作台                                      | 复用已有场景组件，逐步由 Storybook stories 承载；全部调用迁移后再移除旧工作台                             |
| 固定 React 参考应用                                      | 保留并收敛为基线执行端；不升级 vendor 的 React，不把老 React 强行接入新版 React Storybook                 |
| 两套浏览器测试中的重复交互遍历                           | 对照契约逐项合并，复用场景与必要 helper；文档独有加载、内容、布局与编辑器检查保留                         |
| 自建正式/诊断浏览器调度                                  | 使用 Playwright projects、用例筛选、fixtures、webServer 和标准 reporter；必要基线核验保留                 |
| 大量内联附件和分片认证报告                               | 新体系使用 CI artifacts、标准报告与小型运行摘要；保留必要对照图片和失败诊断，不默认内联所有节点的完整样式 |
| Nuxt 文档站、Rslib/Rsbuild 产物构建、Foundation 私有边界 | 本次方案保留；测试运行时采用 Vite 不要求公开产物和文档 builder 一起迁移                                   |

共享构建准备、资源生成和来源核验可能同时被正常文档构建使用。删除旧验收工具前核对调用方，只移除已被替代的职责，不因文件名包含 acceptance 就整段删除。

不把全库示例再复制一份到 Storybook。文档继续引用单份 `.vue` Demo；适合作为契约场景的 Demo 由 story 导入。复杂契约使用已有独立场景；React/Vue 共享场景 ID、数据和结果语义，分别保留框架原生的渲染与事件适配。

## 固定基线与质量边界

唯一行为基线仍为只读 `vendor/semi-design`：`v2.102.0 / cdfba6e520fc83ad871b30f51f36d8af3aaa5a21`。Vue 生态资料仅用于工具选择。上游测试、Adapter、Foundation、样式和文档共同定义契约；上游没有测试的公开行为不能因此被豁免。

每个对照场景保留固定源码依据。复用实际模块来源验证，确保 React 确实运行 vendor，Vue 确实运行公开组件；不以版本文字、镜像 DOM 或历史图片代替基线。Playwright 负责运行与采集，项目只保留薄的差异比较适配层；没有现成工具能自动证明 React 与 Vue 全量等价。

现有关键样式、几何与像素门槛在迁移中保持。历史宿主快照与实时 React/Vue 对照的作用不同，不能直接互相替代；新增快照固定浏览器和宿主环境。[当前门槛](component-contract.md#浏览器验收门槛)、[Playwright 视觉比较](https://playwright.dev/docs/test-snapshots)。

用断言映射判断去重，而非设定“删掉多少用例”的目标：旧断言对应的公开行为、状态、主题、方向、语言和运行环境必须仍有覆盖。迁移期间先保持完整矩阵；确证等价覆盖后才能合并重复步骤。语言会影响布局和可访问名称，dark/RTL 会影响样式，不机械裁剪这些维度。

例如 Button 在组件层保留系统性的 hover/active/focus 验证；文档中的文案、布局、主要点击、源码与 REPL 检查仍逐例执行。只有确认另一语言或另一示例没有新增状态/集成风险，且相应契约已有覆盖时，才合并其重复状态遍历。Modal/Select 在文档容器中的 Portal 或焦点行为仍需保留，不能由 Storybook 通过推导成立。

示例复杂度按真实能力判断：普通 List 与虚拟滚动 List 分开选批。迁移工具不承接缺失虚拟化、拖拽等功能实现，不改变未通过项的状态。

## CI、文档与证据的执行方式

| 改动                             | PR 必跑范围                                                               |
| -------------------------------- | ------------------------------------------------------------------------- |
| 技能、排期、普通仓库文案         | 格式、链接、diff；不启动组件浏览器矩阵                                    |
| 文档正文                         | 文档内容与链接检查；页面生成或路由受影响时加对应构建/页面检查             |
| Demo                             | 示例类型/构建、受影响双语示例及主要操作；触及文档基础设施时扩展相关文档组 |
| 组件实现                         | 组件单测及直接消费者；按实际风险补充组件对照和文档集成                    |
| 主题、公共组件、构建配置、锁文件 | 扩展到受影响组；影响无法可靠确定时保守运行完整相关套件                    |
| 发布候选                         | 全量契约、文档及实际产物门禁；共享构建只准备一次                          |

初期用明确路径、公共入口和既有依赖关系选组，选测逻辑本身要有定向验证。不能仅凭 Git 文件名或静态导入推断所有动态依赖；不为更精细选测新建一套依赖图平台。主题、全局配置与锁文件等变化不能随意排除。

沿用现有 Nuxt 站点，保留双语 Demo 完整性与主要操作覆盖。编辑器编译、重置、热更新、Portal 等公共机制有独立集成用例；各示例仍验证自己的编译结果和必要依赖，不重复测试整套编辑器机制。

新体系的测试结果绑定实际提交、固定 vendor revision、环境和执行范围，详细报告存 CI artifacts。通过且输入未变的运行复用；未运行项不计通过，失败、跳过或 flaky 不可用于认证。构建/执行期间输入变化则本次结果不可作为最终交付证明。

历史报告与旧指纹保留，不改写成新体系结果，不把 346 项待恢复证据自动变为通过。现有 `accepted` 含义在切换前保持；切换时明确记录契约覆盖与文档运行各自的范围和来源，不将新口径折算为旧的逐示例严格 accepted。若继续要求恢复旧 accepted，仍需完成对应旧矩阵。

这是替代自建验收协议的目标设计。CI artifacts 的保存周期、必要对照图片、来源摘要字段与新结果的完成定义，需要在切换切片中验证并写入现有契约后生效；不会因为本方案提交就改变当前证据判定。

## 分阶段落地与退出条件

1. **先修调度与冻结对照。** 对现有 CI 增加明确的改动范围判断；复用现有计时、用例清单与有效证据，记录迁移基线。此步不换 runner，不重跑无关历史矩阵。
2. **建立最小 Vue 标准环境。** 在独立配置中试运行 Vitest/VTU 与 Storybook Vue 3；先核对当前 aliases、SFC/JSX、Node SSR、Prism、Tiptap 和 Worker 所需边界。只做最小编译/加载探针；若迁移需要扩建新编译子系统，则停止该切片并说明，保留旧入口。
3. **从低到高迁移代表切片。** 先 Breadcrumb 或 Switch，再 Popover 的容器/焦点场景，最后 Table 的已有就绪场景。复用旧场景和断言，对照新旧发现范围、失败捕获和实际运行结果；Table 的未就绪拖拽/虚拟化问题不混入工具迁移。
4. **逐组迁移并立即退役旧入口。** 新组通过后移除其旧 runner 调用，避免长期双跑；迁移期允许旧/新 runner 各自负责不同组。单测转换保持事件、异步和 SSR 语义，覆盖率按实际源码核对，不能以百分比接近替代用例等价。
5. **最后切换文档与证据协议。** 按断言映射完成合并，跑一次新体系完整相关门禁；验证报告留存、来源和发布检查。确认调用方全部迁移后移除旧调度、Vue 工作台和不再使用的依赖，更新现有技能与契约。

每个切片都要满足：旧能力有明确去向；有效断言和必要环境未丢；相关检查真实通过；只有一个常规执行入口；剩余缺口如实保留。对关键风险用已知回归或可丢弃的故障注入验证新测试确实会失败，不用“配置能启动”代替测试有效。

同环境、同一覆盖范围记录冷/热运行耗时、构建次数、重复状态验证次数、报告体积、失败定位与修复工作量；有必要时做一次迁移前后对照。尚无这些迁移数据，不承诺节省比例、完成时长或 token 数。只有覆盖保持且成本实测下降，才能认定方案提高了验收效率。
