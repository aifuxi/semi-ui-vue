# 并行文档严格验收

从[批次计划](../../../docs/documentation/batch-plan.md)、覆盖账本和所选批次材料确认当前状态。验收标准与命令见[文档工作流](../../../docs/documentation/workflow.md)，检查选择见[验证入口](../../../docs/testing/validation.md)。只读取本轮所需材料与计时摘要，不加载整份浏览器报告或无关历史记录。

## 先确定本轮能交付什么

- 先复用仍有效的证据；普通新批次只从尚未首次验收的项中选取，不把历史待恢复项算成新增。用户未指定具体批次或顺序时，跨文档分类筛选依赖与实现已就绪的候选，再按示例及完整批次的实际复杂度由低到高推进；文档顺序仅用于成本相近时排序。组件名称只作初筛，虚拟化、拖拽、异步加载等示例按自身集成成本判断。高复杂度项只有用户指定或已证实阻塞后续候选时才提前，说明具体依赖。
- 用账本与已有材料筛出少量候选后再做定向核对；有可独立闭环的合适候选即可选批，不为寻找绝对最低成本扫描整库。静态候选不等于已验证就绪，发现阻塞就保留具体缺口，继续选择独立候选；输入和阻塞证据未变时不重复调查同一问题。
- “一轮验收”不默认包含缺失子系统的完整实现或验收基础设施改造。对候选核对固定片段、真实参考依赖和组件能力，在候选内部优先检查最复杂的交互链；发现 shim、缺失虚拟化/拖拽等核心能力时，先认定为实现缺口，不能等批量编写与整合后再发现。
- 根据就绪程度、共享修复范围和已有耗时数据确定新批次，成本包含依赖准备、诊断、完整矩阵、归档提交与可能的历史证据失效。修改共享输入前按工作流检查影响；会扩大失效范围的候选应重新比较优先级，不为后续候选顺手补齐全库依赖。向用户简短说明选定范围、主要风险与拟运行的检查；有实际计时才给耗时估计，没有计时时保守选批。用户指定的时间或 token 预算优先，预留收尾时间；剩余时间不足以完成完整矩阵和收尾时不启动矩阵，不自行延期。
- 示例接入或已定位的局部契约差异在本轮修复。需要实现新子系统、大幅重构共享组件或改造验收工具时，及时说明范围变化，停止将其滚入本轮；未通过项保留具体缺口，完成可独立闭环的已选工作。用户明确要求这些实现时再纳入范围。
- 同一代表连续暴露不同的共享行为缺口，或累计成本明显偏离选批判断时，按累计影响重新判断范围，停止追加修复；不能以每次都是“小修复”无限延长本轮。测试驱动、临时配置连续失败也计入累计成本；先收敛驱动问题，不能继续用整条验收链调试脚本。转向独立候选也须重新核对剩余预算；没有足够时间完成完整验收与收尾时，保留阻塞并收尾。
- 已定义批次仍执行原完整矩阵，不能删例来制造完成；无法在当前范围闭环的批次保留 pending。全部候选均缺乏验收条件时交付具体阻塞原因，不启动一轮大规模实现。

## 并行必须减少主执行者的重复工作

- 按真实独立边界分工，遵守用户并发上限，传递最小必要上下文。每个子任务明确可写路径，负责所分范围的基线核对、修改与定向回归；交付结论、改动和验证命令/结果，不让主 agent 重新走一遍调查。没有独立任务时不为并行而增加 agent。
- 共享文件只由一个执行者修改。主 agent 处理跨任务依赖和最终验收，不默认接回所有尚未定位的实现问题。共享构建、浏览器服务和证据写入统一调度，其余任务可并行读取或编辑不冲突的范围。

## 定位完成后再扩大验证

- 对高风险交互，最小代表先观察真实参考的关键状态序列，再据此写断言并修改示例；尤其是异步、滚动或第三方集成，静态读码推断的加载条数、按钮门槛和事件顺序不算已验证契约。选择器与节点层级取自实际 DOM、保留的快照或明确源码，滚动断言区分触发前坐标、加载中与追加后高度。代表的完整关键状态链通过后再扩展同类示例与完整矩阵，局部加载态通过不能替代终态验证；已有有效结果不机械叠加 smoke、默认诊断和定点诊断。
- 优先复用仓库现有 fixture、浏览器配置和服务入口。确需临时配置时，先核实解析后的用例集合、服务工作目录和配置合并行为，再开始行为观察；不通过反复启动整套服务试探配置。
- 适用的前置检查与后续运行按依赖顺序执行；前置失败或尚未取得实际退出码时停止依赖它的运行，不能在同一调度调用中无条件继续。长输出从首次运行就保存完整日志、退出码和计时，工具截断时读取已保存结果，不为重新取得输出而重跑检查。
- 失败后保留前序交互与必要输出，先用最小复现定位。下一次运行必须有新的定位证据或对应修复；故障尚未缩小时，不再启动整批诊断/正式矩阵试探下一个问题。需要大幅扩展实现时回到本轮范围判断。
- 正式运行前完成语义审阅、适用静态检查、代表诊断和 `--preflight`，确认实际用例集合、共享输入稳定及报告能够归档。复用代表报告判断体积，不在完整矩阵结束后才设计存储方案。
- 通过且输入未变的检查不重跑；局部修改先验证实际影响，再决定是否需要整库检查。工具或归档改动优先用定向工具测试验证；若现有指纹规则仍会使浏览器证据失效，应在修改前说明代价并判断是否属于本轮，不能改旧指纹或删输入来维持 accepted。
- `--affected --plan` 用于识别影响与复用证据，不作为顺手恢复历史的入口。普通新批次不自动承担历史恢复；失效项保留原报告与指纹，如实计数。发布或明确恢复任务才执行相应历史完整矩阵。

完成范围以有效正式证据为准。更新覆盖账本、队列和必要的批次材料，按根规则仅提交本次修改。交付说明有效新增项、实际检查与耗时、历史失效、剩余缺口和提交号；不另建工作报告，不把累计验收数当作当前有效进度，也不把规则修改本身宣称为已证明节省时间或 token。
