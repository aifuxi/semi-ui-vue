# 并行文档严格验收

在当前仓库执行，所有路径相对实际仓库根解析。用户指定的批次、并发和完成范围优先；未指定时，从维护中的队列选择至多三个可分工批次，完成一轮及必要修复、历史回归后交付，不自动启动下一轮。

## 规范与状态来源

- 项目约束、授权和提交遵守根 AGENTS.md；规则或代码变更沿用 [ai-change-workflow](../ai-change-workflow/SKILL.md)。本 Skill 只维护并行调度。
- 验收标准、命令、缓存、指纹及报告规则统一查 [文档工作流](../../../docs/documentation/workflow.md)，不另建 runner 或放宽门禁。
- 从 [双线计划](../../../docs/documentation/batch-plan.md)、[覆盖账本](../../../docs/documentation/coverage.json)、所选批次配置/映射/证据及相关最近记录接续。重新核验当前状态，不把提示词中的旧数字、组件名单或历史授权当作当前事实。
- 需要可复制的新对话入口时，使用 [启动提示词](../../../docs/documentation/parallel-acceptance-prompt.md)。

## 选批与分工

1. 检查工作区已有修改，按队列顺序和共享依赖选择本轮范围；用户已指定批次时直接核对这些批次。运行现有 `accept:nuxt:batch --affected --plan` 确认起始有效证据和失效范围，不重新全仓摸底。
2. 简述选定批次、文件归属、共享依赖和完成条件后直接推进。默认最多三个子 agent 各负责一个可分离批次，主 agent 保留调度职责；依赖紧密或可用并发不足时减少并发并说明，不强凑三个。此流程要求使用可用的子 agent 能力分工；若不可用则按同一文件归属顺序准备，如实说明未实现 agent 并行。
3. 给每个子任务明确批次、允许修改路径、固定参考入口、交付内容与禁止争用的资源。子 agent 负责本批参考适配、示例/文档、章节/API/迁移审阅、矩阵及批次记录，交付修改清单、已执行检查、未解决问题和准备耗时。
4. 共享组件、主题、参考运行时、工具链、依赖和锁文件由主 agent 统一处理；可明确委派给一个负责人，其他 agent 不同时修改。子 agent 发现共享问题先提交复现与影响分析。覆盖账本、README、队列、最终证据和提交由主 agent 统一维护。

## 统一诊断与冻结

- 子 agent 可并行做不争用输入/输出的低成本检查；共享站点构建、浏览器服务和证据写入只由主 agent 调度，不让各子任务分别启动 runner。
- 诊断或正式 runner 会编译所选批次之外的站点输入。启动前暂停对全部被消费源码的修改，包括其他批次 Demo；不能只冻结当前测试文件。浏览器运行期间其他 agent 可只读审阅，修改待本次运行结束再进行。
- 三批分别完成代表诊断，避免一个失败批次反复阻挡其余批次的缺陷发现；依赖和输出相容时可共用一次调用。主 agent 先确认固定 React 可独立运行，并按适用风险检查 Portal 根与触发器相对位置、关闭重开、焦点、异步状态和动画终态；无对应行为的静态示例不强加这些路径。
- 安排跨批次只读复核，重点看参考适配是否改变行为、归一化是否掩盖差异、代表路径与完整用例范围是否一致。按文档流程核对实际 Playwright 用例清单，不只相信批次声明数量。
- 代表失败先保存证据、区分产品/基线/断言时序/环境，再定点修复。共享缺陷集中处理；修复后的相关代表和静态检查通过，完成最终 diff 与审阅指纹后，冻结正式输入。正式跑完不再补写被追踪的验收说明来使证据失效。

## 正式验收与恢复

- 冻结后重新计算实际失效范围，由主 agent 联合运行所选批次和必要历史回归。复用 runner 核验过内容的准备缓存与证据；有新共享修改时重新计算，不把“只构建一次”当成硬要求。
- 一个调度者串行启动各组，runner 内的 Playwright workers 按现有配置并发。按实际用例清单、交互负载和报告体积分组，避免一次堆入巨大 JSON；不固定复制历史试跑的分组或用例数。
- 正式失败后先保留日志、退出状态、计时和相关 trace/截图，停止后续组。需要中断当前组时确认进程和端口退出，再修改输入或重跑；按现有报告规则重新执行失败批次的完整矩阵，不手工从失败报告抽取通过项认证。
- 仅重跑实际失效阶段和批次，已通过且输入未变的证据继续复用。剩余无法完成时记录真实阻塞及已完成范围，不通过删输入、改旧指纹、增加重试或降低门槛恢复计数。

## 交付

执行本轮批次覆盖与审阅门禁、最终影响计划和工作区差异检查，确认完整证据有效后更新账本、README、队列、必要 changeset 与工作记录，并按根规则提交本次已验收修改。

最终分别报告：新增有效示例数与剩余数、历史重验批次/用例数、有效证据状态、修复内容、实际检查与提交结果。计时区分并行准备墙钟、构建/检查、浏览器、失败排查和整轮耗时；不把各 agent 时间相加作为串行基准，不把历史重验数量算作新增进度，也不承诺未测得的加速倍数。
