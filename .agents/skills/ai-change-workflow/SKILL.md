# AI Change Workflow

在不扩大用户授权范围的前提下，把代码任务推进到可验证、可解释、可维护的状态。若任务属于 Semi Design 组件对齐，同时使用 `semi-ui-vue-vertical-slice` 及适用的 Vue Skill；本 Skill 不替代其专项门禁。

## 1. 建立任务契约

开始前从用户请求和仓库上下文中确认：

- **目标**：最终要改变什么用户可观察结果；
- **验收标准**：用什么行为、测试或产物判断完成；
- **风险点**：最可能破坏的兼容性、数据、接口或运行路径。

信息足够时直接推进，不要求用户重新填写模板。只有缺失信息会显著改变方案或造成高风险时才提问。

## 2. 调查影响范围

- 先读取适用的 `AGENTS.md`、项目文档、工作区状态和目标文件。
- 修改模块前确认其定义、调用方、依赖方、测试和公开契约。
- 跨模块分析优先使用 CodeGraph MCP；MCP 不可用时可用 CodeGraph CLI。每次查询显式指定当前仓库或 worktree 的绝对路径（MCP 的 `projectPath`、CLI 的 `--path`），避免读取其他检出目录的索引。
- CodeGraph 用于符号定位、调用关系和影响范围调查；精确文本查找使用 `rg`。调用关系和 affected tests 是调查线索，动态调用、Vue 自动导入及通过 URL 访问页面的浏览器测试仍需结合源码和测试场景核验，不能用空结果证明没有影响。
- 索引缺失、过期或查询异常时先检查 `codegraph status`；索引就绪后的日常变更使用自动同步，需要时执行 `sync`，全量重建只在首次初始化或确认索引异常时使用。工具不可用时使用 `rg`、语言服务、构建配置和测试补足证据，不因单一工具缺失停止工作。
- 区分本次任务相关修改与用户已有修改；不得覆盖、回退或顺手整理无关内容。

## 3. 判断风险等级

在已授权目标内，根据证据直接实施必要的实现、缺陷修复、基线对齐和验证；不因涉及公共 API、持久化数据、安全边界、生产行为、依赖或架构而自动追加确认。风险评估用于选择调查深度、验证范围和回退方案。

重要取舍说明推荐方案、备选、影响和回退方式。只有超出当前授权、需要用户决定目标，或存在未获授权的不可逆操作时才请求确认；已有授权不重复询问。

## 4. 实施

- 选择满足验收标准的最小改动，保持项目既有模式。
- 注释说明意图和非显然约束；更新或删除已失效注释，不添加形式化噪音。
- 发现需求外问题时记录风险，除非它阻塞验收，否则不扩大修改范围。
- 发现 `AGENTS.md`、`README.md` 或关联文档落后时，在任务范围允许的情况下同步更新，否则在交付中指出。

## 5. 验证

根据风险按比例选择验证手段：

- 先运行最贴近改动的测试，再按需要运行 typecheck、lint、build、集成测试或手动行为验证。
- 对修复任务，尽可能先复现失败，再验证修复后的可观察行为。
- 测试应证明公开行为或关键不变量，不只证明实现细节。
- 记录实际运行的命令、结果及未验证事项；没有运行的检查不得描述为通过。

验证失败时先定位原因。若失败与本次修改无关，保留证据并清楚说明；不得为了制造通过结果而弱化测试。

## 6. 工作记录

满足以下任一条件时，使用 `ai-work/TEMPLATE.md` 在 `ai-work/` 新建记录：

- 高风险变更；
- 涉及多个模块或存在重要方案取舍；
- 用户明确要求计划、审计记录或工作报告；
- 后续维护者需要无法从代码和提交直接恢复的决策背景。

文件名使用 `yyyyMMdd-HHmmss-主题.md`。小范围、低风险且没有重要决策的改动不强制生成报告。

## 7. 交付

最终说明保持简洁并包含：

- 改动结果和原因；
- 已运行的验证及其结果；
- 剩余风险、未验证事项或必要的后续动作。

只有具备运行证据时才声称任务已修复或可运行。团队层面的 Intent Review、Ownership 和合入判断由 `docs/ai-governance.md` 约束。
