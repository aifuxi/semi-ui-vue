# Semi UI Vue 任务分支与 PR 交付

## 开工

- 查看工作区、暂存区和当前分支。新任务从获取到的最新 `origin/master` 建立 `codex/<任务名>` 分支。串行任务复用当前工作区，确需并行隔离时使用独立 worktree。
- 已在对应任务分支时直接继续。已有改动留在本地 `master` 时，先核对改动归属和与远端主线的差异，在保留原工作和暂存状态的前提下把本次改动放到任务分支。任务分支推送前核对 PR 相对 `origin/master` 的差异，只包含本次改动。
- 按项目约定做专项验证、准备 Changeset，并只提交本次任务内容。[项目协作](../../../AGENTS.md)

## 按授权交付

| 用户指令 | 完成条件 |
| --- | --- |
| 实现需求或提交到本地 | 验证通过后在任务分支本地提交。 |
| 推送 | 推送对应任务分支，返回远端分支。 |
| 开 PR | 推送任务分支，创建面向 `master` 的 PR 并返回链接。 |
| 验证通过后合入 `master` | 完成本地验证、提交、推送和开 PR，为该 PR 启用自动 squash，跟进到实际合并并收尾。 |

推送直接使用任务分支。已有同一任务的 PR 时复用它。

## 合入与收尾

1. 对用户明确授权合并的普通 PR，核对目标分支为 `master`，并审阅当前提交的差异。确认仓库已开启自动合并，且 GitHub Actions 的 `Source quality and tooling` 仍是 `master` 的必过检查。用 `gh pr merge <PR 编号> --auto --squash --match-head-commit <已审阅的完整 SHA>` 启用自动合并，由 GitHub 等待必需检查。配置异常时先查明原因，待上述条件恢复后再启用。
2. 跟进 PR 的检查与合并状态，直到实际合入。检查尚未出现时继续等待。CI 失败时定位原因，冲突时核对两边改动。在本次授权范围内更新 PR 前，先用 `gh pr merge <PR 编号> --disable-auto` 关闭已启用的自动合并，更新后审阅新差异并用新 SHA 重新启用。发现仍开放的 PR 出现未经审阅的新提交时，先暂停自动合并，再核对差异和授权范围。
3. 确认 PR 已合并并获取最新 `origin/master`。在可快进且不影响已有工作的情况下同步本地 `master`。核对本地和远端任务分支仍指向本次已合入的工作，退出任务分支后清理未被其他工作使用的分支。有分叉、未保存改动或其他工作占用时保留现场，说明未完成的步骤。
4. 汇报 PR、合并提交及检查结果。普通变更 PR 的合并授权仅覆盖该 PR，版本 PR 和 npm 发布依照[发布手册](../../../docs/releasing.md)与对应授权处理。
